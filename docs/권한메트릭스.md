관련 업무 규칙: 요구사항 문서 - 4. 업무 규칙 · 관련 계약: API 문서 - 외부 HTTP 계약, 서비스 간 동기 계약(각 행의 허용 열에 `METHOD /path` 병기)

사용 가능한 Role: `USER`(참가자) · `HOST`(주최자) · `HELPER`(주최자가 발급하는 현장 입장 검증 전용 임시 계정, 배정된 페스티벌 1개만 접근 가능) · `ADMIN`(플랫폼 운영자) · `STOREHOST`(부스 운영자) — User 테이블 `role` 컬럼에 저장되고 JWT에 포함되어 전달됩니다. 회원가입은 항상 USER로 만들고, HOST는 주최 신청 승인 때 festival-service가 인증 서비스 grantHostRole(`PUT /internal/v1/roles`)을 호출해 부여합니다. ADMIN과 STOREHOST는 부여하는 API나 시드 데이터가 없어 DB에서 `users.role`을 직접 바꿔 부여합니다. HELPER는 셀프 가입이 불가능하고 호스트의 도우미 초대 API로만 활성화 전 상태로 생성되며, 초대 링크에서 비밀번호를 정해 활성화합니다. 페스티벌 종료 24시간 뒤(환경변수 HELPER_ACCOUNT_REVOKE_AFTER_HOURS) 배치가 도우미의 초대·Refresh Token·계정을 물리 삭제합니다.

역할 검사는 두 곳에서 합니다. Gateway는 HELPER만 허용 경로 4개(`GET /api/users/me`, `POST /api/organizer/reservations/verify`, `POST /api/organizer/reservations/verify-code`, `GET /api/organizer/reservations/check-in-stats`)와 공개 라우트 외에는 403으로 막고, 나머지 Role 검사는 각 서비스 계층이 `X-User-Role` 문자열을 비교합니다(Spring Security 인가 규칙은 쓰지 않음). 그래서 아래 표에서 "제한 없음"은 USER·HOST·ADMIN·STOREHOST가 모두 허용되고 HELPER만 Gateway에서 막힌다는 뜻입니다. 예매·결제·환불을 역할 제한 없이 여는 것은 의도된 동작입니다.

## 서비스 간 내부 호출

모든 내부 API는 Gateway 라우트가 없어 외부에서 부를 수 없고, 대상 서비스가 `Authorization: Bearer` 토큰을 환경변수 값과 비교합니다. 토큰이 다르면 401(INVALID_INTERNAL_TOKEN), 헤더가 없으면 401(UNAUTHORIZED)입니다. 토큰 환경변수 이름은 festival → reservation 좌석 생성만 INTERNAL_RESERVATION_TOKEN이고 나머지는 모두 INTERNAL_AUTH_TOKEN입니다. 호출 방향은 서비스 경계 문서의 통신 방향·실패 표와 같습니다.

## 판정 순서

1. 인증 유효성
2. Role
3. Resource 존재와 소유 관계
4. 업무 상태
5. Dependency 결과
6. 허용 또는 안전한 실패

코드의 실제 순서도 이와 같습니다. Gateway가 1(토큰)과 HELPER의 2(허용 경로)를 먼저 판정하고, 각 서비스가 나머지 Role 검사 → 존재·소유 → 업무 상태를 차례로 봅니다. 예외: 서비스 안에서는 소유권보다 존재 확인이 먼저라 없는 리소스는 404, 남의 리소스는 대체로 403이지만, 행사 취소 신청·도우미 계정 관리·주최자의 타인 정산 상세는 남의 리소스도 404로 응답합니다(앞의 두 곳은 존재 은닉 의도가 코드 주석에 있음). Dependency 실패는 권한 오류가 아니라 503(서비스 응답 없음)·502(PG 취소 실패)로 구분하고, 조회 보조 호출(신청자 정보, 환불 미리보기, 주최자명)은 실패해도 본 응답을 막지 않습니다. 단, Gateway의 HELPER 세션 확인은 결과를 알 수 없으면 401로 거부합니다(fail-closed).
