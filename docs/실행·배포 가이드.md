## 새 clone 로컬 재현

운영 배포와 별개로, 새로 clone한 저장소에서 재현하는 절차다. 모든 명령은 저장소 루트 기준이며 백엔드 Gradle 루트는 `backend/`다.

### 1. 공통 준비

```bash
cp .env.example .env
# .env의 각 변수에 로컬 값을 채운다(값은 팀 내부 채널로 전달받고 문서에 쓰지 않는다)
docker compose config --quiet
docker compose up -d core-db
```

- `.env`가 없으면 core-db만 띄우는 경우에도 compose가 설정을 읽는 단계에서 실패한다(아래 실행 기록 참고). 모든 백엔드 서비스가 `env_file: .env`를 선언하기 때문이다.
- core-db는 볼륨 `core-db-data`가 비어 있을 때만 `mysql-init/core-db` 스크립트를 실행한다. 이미 볼륨이 있으면 새 스크립트가 실행되지 않는다(트러블슈팅 문서의 payment-service 재시작 장애 참고).

### 2-A. 컨테이너로 전체 기동

```bash
cd backend && ./gradlew bootJar && cd ..
docker compose up -d --build
```

- `bootJar`를 먼저 하지 않으면 백엔드 이미지 빌드가 `build/libs/*.jar`를 찾지 못한다.
- 로컬에서 nginx까지 포함한 전체 기동은 그대로는 어려울 수 있다. `nginx/nginx.conf`가 `/etc/letsencrypt/live/fevalgo.duckdns.org/` 아래 인증서 파일을 읽고, compose가 호스트의 `/etc/letsencrypt`를 연결하므로 인증서가 없는 로컬 PC에서는 nginx 기동이 실패할 것으로 예상된다. 또 frontend 이미지는 `VITE_API_BASE_URL`을 따로 주지 않으면 운영 도메인을 API 주소로 빌드한다. 이번 작업에서는 실제 기동을 시도하지 않았다(NOT_RUN — 아래 실행 기록 참고). 로컬 화면 확인은 2-B 방식을 권장한다.

### 2-B. 로컬 개발 방식 (bootRun + Vite)

core-db만 컨테이너로 띄우고 나머지는 각각 별도 터미널에서 실행한다. 서비스끼리 기동 순서를 강제하지 않으며, 기동 직후 실패한 서비스 간 호출은 재시도 스케줄러가 흡수한다. gateway는 마지막에 띄우는 것을 권장한다.

```bash
cd backend
./gradlew :auth-service:bootRun          # 8081
./gradlew :festival-service:bootRun      # 8082
./gradlew :reservation-service:bootRun   # 8083
./gradlew :payment-service:bootRun       # 8084
./gradlew :gateway:bootRun               # 8080
```

```bash
cd frontend
npm ci
npm run dev                              # http://localhost:5173
```

- 각 `application.yaml`의 DB·서비스 URL 기본값이 로컬 core-db와 `localhost` 포트(8081~8084)를 가리키므로 별도 설정 없이 연결된다. 외부 연동(메일, Kakao·Google 로그인, PortOne, Gemini, Kakao 지도) 값은 환경 변수로 넣어야 하며, 없으면 해당 기능만 실패한다.
- gateway CORS 허용 origin은 `http://localhost:5173`과 운영 도메인이다. 따라서 Vite 기본 포트(5173)를 바꾸지 않는다.
- bootRun 시 `spring-dotenv`가 어느 위치의 `.env`를 읽는지는 코드로 확정하지 못했다(미확인 - 팀 확인 필요). 확실한 방법은 셸 환경 변수로 넣는 것이다.

### 3. 테스트 실행

```bash
cd backend && ./gradlew test --no-daemon
cd frontend && npm ci && npm run test
```

- 백엔드 테스트는 H2 in-memory(`MODE=MySQL`, `ddl-auto: create-drop`)를 쓰므로 core-db 없이 실행된다. 프론트 테스트는 Vitest + jsdom이다.
- 결과와 명령별 상세는 테스트 전략·테스트 체크리스트 문서에 있다.

## ADMIN·STOREHOST 계정 준비

ADMIN과 STOREHOST 역할을 부여하는 전용 API나 시드 스크립트는 없다. 회원가입으로 만든 계정의 `users.role` 값을 DB에서 직접 바꾼다. 근거: auth-service `User` 엔티티(`@Table(name = "users")`, `role` 컬럼은 enum 이름 문자열로 저장), `Role` enum(`USER`, `HOST`, `HELPER`, `ADMIN`, `STOREHOST`). HOST는 주최 신청 승인으로 부여되고 HELPER는 주최자의 도우미 초대로만 만들어지므로 이 절차로 부여하지 않는다.

- 단계 1: 화면이나 `POST /api/auth/signup`으로 일반 회원가입을 한다(이메일 인증 필요). 가입 직후 역할은 `USER`다.
- 단계 2: core-db의 `auth_db`에 접속한다. 계정·비밀번호는 `.env` 값을 사용하고 명령 기록에 비밀번호를 남기지 않는다.

```bash
docker compose exec core-db mysql -u <AUTH_DB_USERNAME 값> -p auth_db
```

- 단계 3: 가입한 이메일(로그인 아이디, `users.username` 컬럼)로 역할을 바꾼다.

```sql
UPDATE users SET role = 'ADMIN' WHERE username = '<가입 이메일>';
-- 부스 운영자는 'STOREHOST'
SELECT id, username, role FROM users WHERE username = '<가입 이메일>';
```

- 단계 4: 해당 계정으로 로그아웃 후 다시 로그인한다. Access Token의 `role` claim은 발급 시점의 `users.role`로 만들어지므로, 바꾸기 전에 받은 토큰에는 새 역할이 없다.
- 단계 5: ADMIN은 `/admin` 화면, STOREHOST는 페스티벌 상세의 부스 개설과 `/store/booths` 화면으로 확인한다.
- 되돌리려면 같은 방식으로 `role = 'USER'`로 바꾸고 다시 로그인한다.

## 운영 배포 (GitHub Actions + GHCR)

운영 도메인은 `https://fevalgo.duckdns.org/` 이다. 서버 접속 정보와 서버 측 `.env`는 저장소에 없고 GitHub Actions Secrets와 서버에서 관리한다(GitHub Actions가 관리).

| 단계 | 트리거·조건 | 동작 | 근거 |
| --- | --- | --- | --- |
| CI | `main`, `deploy` 브랜치 push·PR | 프론트 `npm ci` → `npm run test` → `npm run lint` → `npm run build`, 백엔드 `./gradlew test --no-daemon`, 테스트 리포트 artifact 업로드 | `.github/workflows/ci.yml` |
| 이미지 빌드·푸시 | `deploy` 브랜치 push에서 CI 테스트 통과 후 | 서비스 5개 `bootJar -x test` 후 이미지 빌드, 프론트는 `VITE_*` build-args로 빌드. `ghcr.io/likelion-backend-24th/final-project-team5-<서비스>:latest`로 GHCR에 push | `ci.yml` |
| CD | CI가 `deploy` 브랜치에서 성공으로 끝난 뒤(`workflow_run`) | GitHub Actions가 SSH로 서버에 접속해 `deploy` 브랜치를 `git pull --ff-only`, `docker-compose.yml`과 `docker-compose.small.yml`을 함께 지정해 이미지 pull 후 `up -d`, nginx에 SIGHUP으로 설정 재적용, 쓰지 않는 이미지·빌드 캐시 정리 | `.github/workflows/deploy.yml` |
- `main`에 merge해도 자동 배포되지 않는다. 배포는 `main` → `deploy` PR을 merge할 때만 일어난다(`ci.yml` 주석). 임시 문서 저장고의 예전 배포 가이드에 있는 "main merge 시 자동 배포" 설명은 현재 워크플로와 다르다.
- 이미지 빌드는 1GB 서버에서 멈추는 문제로 GitHub Actions 러너에서 하고, 서버는 pull만 한다.
- 이미지 태그는 `:latest`만 push한다. 배포 스크립트 주석은 "GHCR 이전 태그를 다시 pull하는 방식으로만 롤백 가능"이라고 적지만, 버전 태그를 따로 push하지 않으므로 실제 롤백 가능한 태그가 있는지는 미확인 - 팀 확인 필요.
- HTTPS 인증서 갱신 자동화는 저장소에 없다(서버 측 설정, 미확인 - 팀 확인 필요).

## 중지·재기동·데이터 초기화

| 명령 | 영향 | 복구 가능성 |
| --- | --- | --- |
| `docker compose stop` / `docker compose start` | 컨테이너만 멈추고 다시 시작한다. DB 볼륨·업로드 이미지 유지 | 데이터 손실 없음 |
| `docker compose restart <서비스>` | 해당 서비스만 재시작. 진행 중 요청은 끊기며, 재시도 스케줄러 대상(APPROVAL_PENDING, PUBLISH_PENDING, 웹훅 FAILED 등)은 DB에 남아 재기동 후 다시 처리된다 | 데이터 손실 없음 |
| `docker compose up -d --build <서비스>` | 이미지를 다시 빌드하고 컨테이너를 교체한다(백엔드는 먼저 `bootJar`) | 데이터 손실 없음 |
| `docker compose down` | 컨테이너·네트워크 삭제. 이름 있는 볼륨 `core-db-data`와 호스트의 업로드 이미지 폴더는 남는다 | `docker compose up -d`로 복구 |
| `docker compose down -v` | `core-db-data` 볼륨까지 삭제되어 4개 스키마의 모든 데이터(회원, 페스티벌, 예매, 결제, 정산)가 사라진다. 다음 기동 때 init 스크립트가 다시 실행된다 | 별도 DB 백업이 없으면 복구 불가. 운영 서버에서는 실행 금지 |
| 업로드 이미지 폴더 삭제(`HOST_SAVED_IMAGE` 경로) | 페스티벌·부스 이미지 파일이 사라지고 DB에는 URL만 남는다 | 백업이 없으면 복구 불가 |
