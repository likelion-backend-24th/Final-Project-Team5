### 환경 변수 이름 (값은 적지 않음)

## 새 clone 로컬 재현

### A. docker compose 한 번으로 전체 기동 (권장)

```bash
cp .env.example .env
docker compose -f docker-compose.yml -f docker-compose.local.yml up -d --build
# → http://localhost:8088
```

- 백엔드 5개는 `backend/Dockerfile.local`이 이미지 안에서 `bootJar`까지 빌드한다. 첫 빌드는 약 2분, 캐시가 있으면 약 40초(2026-09-29 측정).
- nginx는 `nginx-local/default.conf`(HTTP)를 쓰고, 화면과 API를 같은 출처(http://localhost:8088)로 제공한다.
- 프로젝트 이름 `fevalgo-local`, 컨테이너 이름 `fevalgo-local-*`, 새 DB 볼륨을 써서 운영형 compose나 이미 떠 있는 개발용 컨테이너와 섞이지 않는다. 호스트에는 8088만 연다.
- auth-service가 로컬 전용 시드 계정을 만든다: 운영자 `local-admin@fevalgo.test`, 부스 운영자 `local-storehost@fevalgo.test`, 참가자 `local-user@fevalgo.test`(비밀번호는 `.env`의 `LOCAL_SEED_PASSWORD`). 같은 이메일이 있으면 다시 만들지 않는다.
- 첫 기동 때 MySQL 초기화를 기다리는 동안 서비스가 한 번 재시작될 수 있다(restart 정책으로 정상화).
- 메일 인증 가입·소셜 로그인·PortOne 결제 완료·Gemini·카카오맵은 `.env`에 실제 키를 넣었을 때만 동작한다. 카카오맵 JavaScript 키는 운영 도메인만 허용돼 localhost에서는 지도가 뜨지 않는다.

### B. 개발 방식 (bootRun + Vite)

core-db만 컨테이너로 띄우고 나머지는 각각 실행한다. 서비스 기동 순서는 강제하지 않으며, 기동 직후 실패한 서비스 간 호출은 재시도 배치가 흡수한다.

```bash
docker compose up -d core-db
cd backend
./gradlew :auth-service:bootRun          # 8081
./gradlew :festival-service:bootRun      # 8082
./gradlew :reservation-service:bootRun   # 8083
./gradlew :payment-service:bootRun       # 8084
./gradlew :gateway:bootRun               # 8080
cd ../frontend && npm ci && npm run dev  # http://localhost:5173
```

- 각 `application.yaml`의 DB·서비스 URL 기본값이 로컬 core-db(3307)와 localhost 포트를 가리킨다. 비밀값 검사는 기본 꺼져 있어 경고만 남긴다.
- 각 서비스는 spring-dotenv(4.0.0)로 실행 디렉터리의 `.env`를 읽는다. `./gradlew :auth-service:bootRun`의 실행 디렉터리는 모듈 폴더이므로, 그 위치에 `.env`를 두거나 셸 환경 변수로 넣는다.
- gateway CORS 허용 origin은 `http://localhost:5173`과 운영 도메인이라 Vite 포트를 바꾸지 않는다. Refresh 쿠키는 항상 Secure라 http 로컬에서는 localhost에서만 전달된다.

### 테스트 실행

```bash
cd backend && ./gradlew test --no-daemon
cd frontend && npm ci && npm run test
```

- 백엔드 테스트는 H2 in-memory(`MODE=MySQL`, `ddl-auto: create-drop`)라 core-db 없이 실행된다. 결과와 명령별 상세는 테스트 전략·테스트 체크리스트 문서에 있다.

## 운영자(ADMIN)·부스 운영자(STOREHOST) 계정

- 로컬 재현: 위 시드 계정을 쓴다.
- 운영: 부여 API가 없어 가입한 계정의 `users.role`을 DB에서 바꾼다. 운영 DB 쓰기는 팀 확인 후 실행한다.

```sql
UPDATE users SET role = 'ADMIN' WHERE username = '<가입 이메일>';  -- 부스 운영자는 'STOREHOST'
```

- 바꾼 뒤 다시 로그인해야 한다(Access Token의 role은 발급 시점 값). HOST는 주최 신청 승인으로, HELPER는 주최자의 도우미 초대로만 만들어진다.

## 운영 배포 (GitHub Actions + GHCR)

운영 도메인은 https://fevalgo.duckdns.org/ 이다. 서버 접속 정보와 서버 `.env`는 저장소에 없고 GitHub Actions Secrets와 서버에서 관리한다.

| 단계 | 트리거·조건 | 동작 | 근거 |
| --- | --- | --- | --- |
| CI | `main`, `deploy` 브랜치 push·PR | 프론트 `npm ci` → `npm run test` → `npm run lint` → `npm run build`, 백엔드 `./gradlew test --no-daemon`, 테스트 리포트 artifact 업로드 | `.github/workflows/ci.yml` |
| 이미지 빌드·푸시 | `deploy` 브랜치 push에서 CI 테스트 통과 후 | 서비스 5개 `bootJar -x test` 후 이미지 빌드, 프론트는 `VITE_*` build-args로 빌드. `ghcr.io/likelion-backend-24th/final-project-team5-<서비스>:latest`로 push | `ci.yml` |
| CD | CI가 `deploy` 브랜치에서 성공한 뒤(`workflow_run`) | SSH로 서버에서 `deploy` 브랜치 `git pull --ff-only`, `docker-compose.yml`  • `docker-compose.small.yml`로 이미지 pull 후 `up -d`, nginx에 `docker kill -s HUP nginx`로 설정 재적용, `docker image prune -af`·`docker builder prune -af` | `.github/workflows/deploy.yml` |
- `main`에 병합해도 배포되지 않는다. 배포는 `main` → `deploy` PR을 병합할 때만 일어난다.
- 운영 compose는 비밀값 검사가 켜져 있다. 새 비밀값 환경변수를 추가했다면 서버 `.env`에 먼저 넣고 배포한다.
- 이미지는 `:latest`만 push하므로 이전 버전 태그로 되돌리는 롤백은 할 수 없다. 되돌리려면 이전 커밋을 deploy에 다시 병합해 이미지를 새로 빌드한다.
- HTTPS 인증서는 서버의 Let's Encrypt 설정을 쓰며(compose가 `/etc/letsencrypt`와 `certbot-webroot`를 연결), 갱신 스크립트는 저장소에 없다.

### 배포 직후 스모크 확인

1. `https://fevalgo.duckdns.org/`와 `GET /api/festivals`가 200인지 확인한다.
2. 로그인 후 `GET /api/users/me`가 200인지 확인한다(인증·Gateway·auth-service).
3. 좌석형 페스티벌을 새로 공개했다면 1분 안에 PUBLISH_PENDING에서 PUBLISHED로 바뀌는지 확인한다(서비스 간 URL·내부 토큰, 트러블슈팅 6).
4. 서버에서 `docker ps`로 8개 컨테이너가 Up인지, 재시작을 반복하는 컨테이너가 없는지 확인한다(비밀값 검사 실패·DB 연결 실패는 여기서 드러난다).

### 서비스 추가 체크리스트

- DB 연결 수: 서비스 수 × Hikari 풀(현재 5) + 여유가 core-db `max-connections`(small override 60) 안에 들어오는지(트러블슈팅 1)
- compose `environment`에 다른 서비스 URL을 컨테이너 이름으로 지정(`localhost` 기본값 폴백 금지, 트러블슈팅 6)
- Gateway route와 공개 경로·HELPER 허용 목록, 내부 API는 Gateway에 라우팅하지 않기
- 새 스키마·계정은 `mysql-init/core-db` 스크립트에 추가하고, 기존 볼륨에는 수동 실행
- 비밀값을 `RequiredSecretsValidator`와 `.env.example`에 추가

### 외부 API 연동 체크리스트

- 제공사 콘솔에서 제품 활성화와 허용 도메인(운영·로컬) 등록(트러블슈팅 9)
- 실제 응답 샘플로 매핑(예: 시·도 축약형)과 오류 응답을 확인하고, 폴백이 결함을 가리지 않는지 확인
- 키는 서버 전용(`.env`)과 브라우저 공개용(`VITE_*`)을 구분하고, Timeout을 ClientConfig에 지정

## 중지·재기동·데이터 초기화

| 명령 | 영향 | 복구 가능성 |
| --- | --- | --- |
| `docker compose stop` / `start` | 컨테이너만 멈추고 다시 시작한다. DB 볼륨·업로드 이미지 유지 | 데이터 손실 없음 |
| `docker compose restart <서비스>` | 해당 서비스만 재시작. 재시도 배치 대상(APPROVAL_PENDING, PUBLISH_PENDING, 웹훅 FAILED, 결과 미정 결제 등)은 DB에 남아 재기동 후 다시 처리 | 데이터 손실 없음 |
| `docker compose down` | 컨테이너·네트워크 삭제. 이름 있는 볼륨과 업로드 이미지 폴더는 남는다 | `up -d`로 복구 |
| `docker compose down -v` | DB 볼륨까지 삭제되어 4개 스키마의 모든 데이터가 사라지고, 다음 기동 때 init 스크립트가 다시 실행된다 | 백업이 없으면 복구 불가. 운영 서버에서는 실행 금지(로컬 재현은 `-f docker-compose.yml -f docker-compose.local.yml`을 붙이면 `fevalgo-local` 볼륨만 대상) |
| 업로드 이미지 폴더 삭제 | 페스티벌·부스 이미지 파일이 사라지고 DB에는 URL만 남는다 | 백업이 없으면 복구 불가 |
