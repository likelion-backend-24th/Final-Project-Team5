## 1. payment-service 무한 재시작으로 운영 서버 전체가 느려짐

| 항목 | 기록 |
| --- | --- |
| 시각·영향 | 2026-09-08, Sprint 2. payment-service를 처음 배포한 직후 컨테이너가 계속 재시작하며 1vCPU 서버를 점유해, 로그인을 포함한 모든 API 응답이 극도로 느려졌다. |
| 관련 Story | Story 7 (#36) 결제 도입과 함께 발생(배포·운영) |
| 관련 계약·Test | 자동 테스트 없음(인프라 설정). 근거 커밋 `742bb99`, `docker-compose.small.yml` 주석, 각 서비스 `application.yaml`의 `hikari.maximum-pool-size` |
| 재현·증상 | 배포 후 payment-service가 DB 연결 실패와 "Too many connections"로 재시작을 반복했다. |
| 확인한 원인 | (1) core-db 볼륨이 payment_db 도입 전부터 있어 `mysql-init/core-db/03-payment-db.sql`이 실행되지 않아 스키마·계정이 없었다. (2) payment-service Dockerfile만 exec-form ENTRYPOINT라 `JAVA_OPTS`(힙 상한)가 적용되지 않았다. (3) MySQL `max-connections=30`이 기존 3개 서비스의 기본 풀(10개씩)로 이미 차 있었다. |
| 조치 | 운영 DB에 init 스크립트를 수동 실행, payment-service Dockerfile을 다른 서비스와 같은 shell-form(`sh -c "exec java $JAVA_OPTS -jar app.jar"`)으로 통일, 서비스별 Hikari 풀 5개와 core-db `--max-connections=60`으로 조정. |
| 정상·실패 회귀 | 코드상 확인: 백엔드 Dockerfile 5개 ENTRYPOINT 동일, 4개 서비스 `maximum-pool-size: 5`, `docker-compose.small.yml`의 `--max-connections=60`. 자동 회귀 테스트 없음 |
| Backlog·설계 조정 | 실행·배포 가이드에 "core-db 볼륨이 이미 있으면 init 스크립트가 다시 실행되지 않는다"와 서비스 추가 체크리스트(DB 연결 수 = 서비스 수 × 풀 크기) 기록 |

## 2. 입장 검증에서 컨테이너 UTC와 입력 시각(KST)이 9시간 어긋남

| 항목 | 기록 |
| --- | --- |
| 시각·영향 | 2026-09-08 ~ 09-09, Sprint 2. 현장 입장 검증(공연 시작 전 입장 차단)이 입력 시각을 서버의 현재 시각과 비교하면서, 컨테이너 기본 UTC 때문에 판정이 9시간 어긋났다. |
| 관련 Story | Story 10 (#39) 현장 입장 |
| 관련 계약·Test | `POST /api/organizer/reservations/verify`. `CheckInAcceptanceTest`(커밋 `9003aac`에서 수정, 예: `공연_시작_전에는_입장_처리되지_않는다`) |
| 재현·증상 | 주최자가 datetime-local로 입력한 시각(타임존 없는 KST)을 UTC로 도는 컨테이너가 `LocalDateTime.now()`와 비교해, 시작 여부 판단이 9시간 틀렸다. core-db도 `SELECT NOW()`가 9시간 느렸다. |
| 확인한 원인 | 컨테이너 TZ 미설정(UTC)과 코드의 암묵적 서버 타임존 의존(커밋 `9003aac` 본문) |
| 조치 | `docker-compose.yml`의 Java 서비스와 core-db에 `TZ: Asia/Seoul`(`5c53f8b`). 입력 시각과 현재를 비교하는 곳은 `app.timezone`(기본 Asia/Seoul)으로 `LocalDateTime.now(zone)` 사용. reservation-service에 `hibernate.jdbc.time_zone: UTC`를 지정해 Instant 컬럼 변환 기준 유지 |
| 정상·실패 회귀 | `CheckInAcceptanceTest` 18개 PASS |
| Backlog·설계 조정 | 일부 스케줄러·챗봇은 `LocalDateTime.now()`를 쓰지만 컨테이너 TZ 통일로 같은 결과(아키텍처 문서의 타임존 결정) |

## 3. 새로고침을 연달아 하면 로그인이 풀림

| 항목 | 기록 |
| --- | --- |
| 시각·영향 | 2026-09-10, Sprint 2. 라이브에서 로그인 상태로 새로고침을 빠르게 여러 번 하면 사용자가 로그아웃됐다. |
| 관련 Story | Story 2 (#8) 로그인·재발급 |
| 관련 계약·Test | `POST /api/auth/reissue`. `UserAuthAcceptanceTest`(폐기 5초 안 재사용 복구, 5초가 지난 재사용 전체 폐기), `AuthServiceTest` |
| 재현·증상 | 새로고침마다 재발급이 호출되고, 이전 재발급 응답이 반영되기 전에 이미 폐기된 Refresh Token으로 다시 재발급을 시도했다. |
| 확인한 원인 | Access Token이 메모리에만 있어 새로고침마다 재발급이 필요했고, Rotation 경합을 재사용 탐지가 탈취로 판정해 모든 세션을 폐기했다(PR #200 본문). |
| 조치 | 백엔드는 폐기 후 5초(`REUSE_GRACE_PERIOD`) 안의 재사용이면 `replaced_by_token_id` 체인을 따라 최신 토큰으로 교체하고, 5초가 지난 재사용만 전체 폐기(PR #200). 프론트는 Access Token을 저장소에 캐싱해 만료 전 새로고침에서는 재발급을 하지 않게 했고, 이후 탭 간 로그인 동기화(PR #215)로 localStorage와 storage 이벤트를 사용 |
| 정상·실패 회귀 | `UserAuthAcceptanceTest` 10개 PASS |
| Backlog·설계 조정 | 아키텍처 문서 결정 기록 "Refresh Token Rotation + 재사용 탐지에 5초 유예 구간" |

## 4. 주최자 승인이 APPROVAL_PENDING에 멈춤

| 항목 | 기록 |
| --- | --- |
| 시각·영향 | 2026-09-13, Sprint 2. 운영자가 승인한 주최 신청이 "대기중"(APPROVAL_PENDING)에 머물렀다. 신청자 HOST 권한은 실제로 부여된 상태였다. |
| 관련 Story | Story 4 (#10) 주최 신청 심사·권한 부여 |
| 관련 계약·Test | `PATCH /api/admin/host-applications/{id}`, 내부 `PUT /internal/v1/roles`(applicationId 멱등키). `HostApplicationReviewAcceptanceTest`(`approvingKeepsApprovalPendingWhenAuthServiceCallFails`, `retryingApprovalAfterFailureRecoversToApproved`, `cannotRejectWhileApprovalIsPending`), `HostApplicationServiceTest`(`retryPendingApprovalsMarksStuckApplicationApproved`) |
| 재현·증상 | festival-service → auth-service 역할 부여 호출의 응답이 read timeout(당시 2초)을 넘기면 예외가 조용히 처리되고 신청이 APPROVAL_PENDING으로 남았다. |
| 확인한 원인 | auth-service 응답 지연이 read timeout을 넘김(역할 부여 자체는 성공, 커밋 `6beb103` 본문) |
| 조치 | read timeout 5초(connect 1초, `AuthServiceClientConfig`), `HostApplicationApprovalRetryScheduler`가 60초마다 30초 넘게 APPROVAL_PENDING인 신청을 같은 applicationId로 재호출해 APPROVED로 확정, 삼키던 예외는 로그로 남김, 프론트에 "승인 처리중" 배지·재시도 버튼 |
| 정상·실패 회귀 | `HostApplicationReviewAcceptanceTest` 8개, `HostApplicationServiceTest` 15개 PASS |
| Backlog·설계 조정 | "중간 상태 커밋 → 외부 호출 → 재시도 배치" 패턴을 페스티벌 공개(PUBLISH_PENDING)에도 사용(시퀀스 문서 실패·복구 흐름) |

| 정상·실패 회귀 | `SeatedFestivalPublishRetryTest` 2개, `InternalSeatGenerationAcceptanceTest` 3개, `AdminFestivalControllerAcceptanceTest` 8개, `SeatedReservationStockAcceptanceTest` 3개 PASS |
